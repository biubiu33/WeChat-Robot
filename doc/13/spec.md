# MewCode 微信桌面聊天机器人 V1 Spec

状态：已批准

## Background

MewCode 当前是一个运行在终端中的 Coding Agent，已经具备模型调用、Agent 循环、会话、上下文、权限、MCP、Skills 和记忆等能力，但只能通过 TUI 与用户交互。

本项目需要让 MewCode 能够通过 Windows 微信桌面客户端与普通微信好友聊天。第一版只验证最核心链路：微信好友发送文字消息，本地程序通过 UI Automation 读取消息，MewCode 生成回复，本地程序再通过 UI Automation 将回复发送给原好友。

第一版运行在本地 Windows 电脑上，不考虑服务器部署。

## Goals

- 让 MewCode 可以在不启动 TUI 的情况下处理微信消息。
- 通过 Windows UI Automation 接入当前登录的普通微信账号。
- 支持白名单好友发送文字消息并收到 MewCode 回复。
- 每个好友拥有独立、可恢复的对话上下文。
- 防止机器人回复自己的消息或重复处理同一条消息。
- 保持现有 MewCode TUI 功能和使用方式不受影响。
- 建立安全、稳定的最小闭环，为后续群聊、附件和更多 Agent 能力提供验证基础。

## Functional Requirements

### F1：运行入口

- 系统应提供独立的微信机器人启动入口。
- 启动微信机器人时不应打开或依赖 MewCode TUI。
- 原有 MewCode TUI 入口应继续正常工作。
- 微信机器人和 MewCode TUI 应复用同一套 Agent 能力，不得维护两套不同的 Agent 循环。

### F2：运行环境

- 第一版只支持 Windows。
- 第一版只支持一个已登录的微信桌面客户端实例。
- 第一版以微信桌面客户端 4.1.12.55 为唯一兼容与验收基准。
- 微信通道的配置由 MewCode 独立维护，不读取或继承 fake-wx-account 的配置、默认值、控件选择器及操作节拍。
- 微信机器人启动时应检查微信客户端和 UI Automation 是否可用。
- 微信不可用时，程序应输出明确错误，不得静默失效或无限崩溃重启。

### F3：消息监听

- 系统应能够发现微信桌面客户端中新到达的私聊文字消息。
- 系统只处理启动后新到达的消息。
- 启动时已经存在的历史消息不得被当作新消息自动回复。
- 系统应识别消息所属会话及发送者。
- 系统应忽略机器人自己发送的消息。
- 系统应忽略群聊、图片、语音、文件、视频、分享卡片和系统通知。

### F4：好友访问控制

- 系统应支持配置允许使用机器人的好友白名单。
- 只有白名单好友的私聊文字消息可以触发 MewCode。
- 非白名单好友的消息应被忽略，且不调用模型。
- 白名单判断不得由模型决定。
- 微信显示名称不是可靠唯一标识时，系统应避免把两个同名好友错误地映射为同一会话。

### F5：消息去重

- 每条微信消息最多触发一次 Agent 任务。
- UI Automation 重复扫描到同一消息时，不得产生重复回复。
- 程序自己发送的回复不得再次进入 Agent。
- 去重信息应能够覆盖正常的窗口刷新、切换会话和短时重复扫描。

### F6：会话隔离

- 每个微信好友应对应一个独立的 MewCode 会话。
- 不同好友之间不得共享可见对话历史。
- 一个好友的消息和回复不得出现在另一个好友的模型上下文中。
- 联系人与 MewCode 会话的映射应持久化。
- 程序正常重启后，同一好友应能继续之前的会话。
- 普通好友不得读取或污染其他好友及 MewCode 主人的长期记忆。

### F7：Agent 调用

- 白名单好友的新文字消息应作为一条用户消息提交给 MewCode。
- 微信入口应使用适合日常聊天的独立系统提示，不应直接向好友展示终端 Coding Agent 的操作说明。
- 第一版只使用 MewCode 的最终文本回答。
- 模型推理过程、工具调用过程、Token 统计和内部错误不得直接发送给微信好友。
- Agent 达到最大步骤、超时或取消时，应结束当前任务，不得无限运行。

### F8：微信权限限制

- 第一版微信好友会话统一处于受限模式。
- 微信好友不得通过消息执行本机命令。
- 微信好友不得读取、修改或删除本机文件。
- 微信好友不得安装 Skills。
- 微信好友不得调用可能访问本机敏感资源的 MCP 或其他外部能力。
- 微信消息内容不得改变上述权限。
- 第一版不提供微信主人专属的完整工具权限。

### F9：任务队列

- 第一版所有微信消息使用一个全局先进先出队列。
- 同一时间最多运行一个微信 Agent 任务。
- 同一好友连续发送多条消息时，应按接收顺序处理。
- 不同好友同时发送消息时，也应按进入队列的顺序处理。
- 正在执行的任务不得因为后续新消息到达而被静默覆盖。
- 队列中的每条消息完成后，才能处理下一条。

### F10：取消

- 白名单好友可以发送 `/cancel` 请求取消自己当前正在运行的任务。
- `/cancel` 不应作为普通聊天内容提交给模型。
- 一个好友不得取消其他好友的任务。
- 没有正在运行的任务时，`/cancel` 应返回简短、明确的提示。
- 取消后，队列应继续处理下一条消息。

### F11：回复发送

- Agent 正常完成后，系统应把最终文本发送回触发任务的原微信会话。
- 发送前应再次确认回复目标，避免因微信窗口切换而发错联系人。
- 会话切换和文字发送不得移动或点击鼠标；允许激活微信并短暂占用键盘焦点。
- 长回复应自动拆分为多条消息，并保持顺序。
- 第一版不发送流式增量消息。
- 第一版不发送图片、语音、文件和视频。
- 最终文本为空时不得发送空白微信消息。

### F12：错误处理

- 模型请求失败时，应向原好友发送一次简短失败提示。
- UI Automation 发送失败时，应记录错误，不得把回复发给其他联系人。
- 微信窗口暂时不可用时，系统应进行有限次数恢复尝试。
- 恢复失败后，系统应保持可诊断状态，不得无限高频重试。
- 单条消息处理失败不得导致整个微信机器人退出。
- 错误消息不得包含 API Key、系统提示、完整堆栈或本机敏感路径。

### F13：配置

第一版至少应允许配置：

- 微信机器人是否启用。
- 好友白名单。
- MewCode Provider。
- 微信聊天使用的系统提示或角色描述。
- Agent 单次任务超时时间。
- 回复最大分段长度。
- 日志级别。

敏感凭据不得写入可提交到版本库的默认配置。

### F14：日志和状态

- 系统应记录启动、停止、微信可用状态、消息接收、任务开始、任务结束和发送结果。
- 日志应能够区分不同微信会话，但不应默认记录完整私聊正文。
- 日志不得输出 API Key、访问令牌或其他凭据。
- 系统停止时应清晰结束监听和正在运行的任务。

## Non-Functional Requirements

### N1：兼容性

- 现有 MewCode TUI 行为、命令、Provider、MCP、Skills、会话和测试不得因微信功能而回退。
- 非 Windows 环境仍可安装和使用普通 MewCode。
- 非微信用户不应被强制安装 Windows UI Automation 相关依赖。

### N2：安全性

- 微信消息是外部不可信输入。
- 权限控制必须由程序强制执行，不能只依赖系统提示。
- 不同好友的会话内容必须隔离。
- 默认配置不得开放本机命令、文件和敏感工具。
- 日志和错误回复不得泄露内部信息。

### N3：可靠性

- 同一消息不得重复回复。
- 自己发送的消息不得触发循环。
- 回复不得发送到错误会话。
- 单条消息异常不得终止整个进程。
- 微信窗口最小化或被其他窗口覆盖时，系统应尽力恢复并继续工作。

### N4：性能

- 在微信客户端正常、桌面未锁定且没有排队任务时，新文字消息应在 5 秒内进入处理流程。
- UI Automation 监听不得持续占用一个完整 CPU 核心。
- 第一版允许 Agent 任务全局串行，不要求并行吞吐。

### N5：可测试性

- 消息过滤、白名单、去重、会话映射、权限限制、任务排队和取消应能在不启动真实微信的情况下验证。
- 真实微信收发应提供人工冒烟验证方式。
- 测试不得自动向真实好友发送消息。

## Out of Scope

第一版不包含：

- 群聊和群聊 `@` 触发。
- 图片识别和图片发送。
- 语音识别、语音回复和 TTS。
- 文件、视频和分享卡片处理。
- 主动发送、定时任务、群发和每日热点。
- 多微信账号或多微信客户端实例。
- Linux、macOS、Docker 和服务器部署。
- Web 管理后台和系统托盘界面。
- 微信内远程审批。
- 微信主人完整控制本机的能力。
- 好友调用 Bash、文件工具、Skills、MCP 或 Sub-agent。
- 好友级长期记忆和跨会话用户画像。
- 通用多渠道框架。
- 对其他微信版本提供兼容保证。
- “文件传输助手”等未暴露标准消息列表和输入框的特殊会话。
- 绕过微信登录验证或账号安全机制。

## Acceptance Criteria

### AC1：启动

- 在 Windows 上登录一个兼容版本微信后启动机器人，程序成功进入监听状态。
- 微信未启动时，程序给出明确错误且不产生无限崩溃循环。
- 启动微信机器人不需要启动 TUI。

### AC2：基本聊天闭环

- 白名单好友发送一条私聊文字消息后，MewCode 正常生成回答。
- 回答只发送到该好友会话。
- 每条入站消息只产生一组最终回复。

### AC3：访问控制

- 非白名单好友发送消息时，不调用模型且不发送回复。
- 白名单好友要求执行命令、读取文件或修改文件时，相关操作不会被执行。
- 聊天内容无法改变好友权限。

### AC4：消息过滤

- 机器人自己发送的回复不会再次触发 Agent。
- 群聊消息不会触发 Agent。
- 图片、语音、文件和系统通知不会触发 Agent。
- 程序启动时不会回复已有历史消息。

### AC5：去重

- 同一消息被 UI Automation 连续观察多次时，只回复一次。
- 切换微信会话再切回后，已处理消息不会再次回复。

### AC6：会话隔离

- 好友 A 和好友 B 分别聊天时，各自拥有独立上下文。
- 好友 A 的消息不会出现在好友 B 的回答或模型上下文中。
- 重启程序后，两名好友仍分别恢复自己的会话。

### AC7：队列顺序

- 两名好友近乎同时发送消息时，系统按入队顺序处理。
- 第二条任务等待第一条任务结束后再执行。
- 后到消息不会覆盖正在运行的任务。

### AC8：取消

- 好友发送 `/cancel` 后，只取消该好友当前任务。
- 取消不会终止机器人进程。
- 取消后队列继续处理后续消息。

### AC9：发送安全

- Agent 运行期间人工切换微信窗口，最终回复仍发送给原目标或安全失败。
- 无法确认目标会话时，系统不得向当前可见的其他联系人发送回复。
- 自动切换好友和发送文字时鼠标位置保持不变，且目标或焦点复核失败时不发送。
- 长回复按顺序分段发送。

### AC10：异常恢复

- 模型请求失败时，好友只收到一次简短失败提示。
- 单条消息处理失败后，后续消息仍可正常处理。
- 微信窗口最小化后，新消息仍能被发现，或系统输出明确的不可用状态。

### AC11：兼容性

- 原有 MewCode TUI 可以正常启动和完成一次 Agent 对话。
- 原有自动化测试继续通过。
- 非 Windows 环境安装普通 MewCode 时不要求安装微信 UI Automation 依赖。

### AC12：隐私

- 日志中不出现 API Key、令牌或完整系统提示。
- 默认日志不保存完整好友聊天正文。
- 不同好友之间不存在可观察的会话和记忆泄露。
